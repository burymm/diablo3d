# 02. Архитектура: варианты и рекомендация

## Общая схема

```
┌──────────────────────────────┐        ┌───────────────────────────────┐
│  Diablo 1: The Hell 4        │        │  Garry's Mod (Source engine)  │
│  (авторитетная симуляция)    │        │  (3D-представление + ввод)    │
│                              │        │                               │
│  игровая логика, мир         │        │  GMod-аддон/gamemode (Lua)    │
│         │                    │        │        ▲        │             │
│         ▼                    │        │        │        ▼             │
│  [TH4 EXPORT/HOOK] ────┐     │        │   [GMod-мост]                 │
└────────────────────────┼─────┘        └────────┼───────┼─────────────┘
                         │  состояние мира       │       │ команды игрока
                         └──────►[ ПРОТОКОЛ ]────┘◄──────┘
                                 (IPC/сокет/HTTP)
```

Мост пересекает границу **двух процессов**. Значит нужен транспорт (см. `05-most-i-api.md`).

## Развилка №1: как «достать» состояние из TH4

### Вариант A. Инструментировать исходники TH4 (встроить экспорт в игру)
- Мы владеем исходниками → добавляем слой, который каждый тик читает глобальные массивы
  мира и сериализует их.
- **Плюсы:** надёжно, стабильные смещения (мы сами их задаём), доступ к логике и событиям,
  возможность принимать команды извне на уровне функций игры.
- **Минусы:** нужно собрать TH4 из исходников (MSVC, Win32, `fxc.exe`); наш билд — это форк,
  который придётся поддерживать при обновлениях мода.

### Вариант B. Внешнее чтение памяти процесса TH4 (без правки игры)
- Отдельный процесс читает `TH4.exe` через `ReadProcessMemory` по известным смещениям.
- **Плюсы:** не трогаем игру, быстрый прототип.
- **Минусы:** хрупко (смещения зависят от сборки), нет событий и инъекции команд
  «изнутри», возможны проблемы с античит-подобной защитой (в TH4 её нет, но всё же).
- Зацепка: в репо уже есть огромная база реверса — `vendor/the-hell-4-src/lib/txt/*`
  (указатели, адреса данных, `__POINTERS.txt`, `__DATA ADDRESSES.txt`).

### Вариант C. Гибрид (рекомендуется на старте)
- Прототип — B (читаем память по документированным смещениям, быстро получаем данные).
- Боевой путь — A (переносим экспорт в исходники, делаем стабильный API).
- C позволяет не ждать успешной сборки TH4, но целимся в A.

## Развилка №2: как выглядит запуск (кто «хозяин» экрана)

### Форма 1. Overlay / компаньон (2 окна)
- TH4 запущен (можно свернуть/приглушить рендер), GMod подключён и показывает 3D.
- **Плюсы:** минимум изменений, легко отлаживать, TH4 работает штатно.
- **Минусы:** два приложения, TH4 всё ещё рисует 2D-окно.

### Форма 2. Headless-сервер
- TH4 запускается с выключенным рендером (в конфиге уже есть `BackgroundDraw off`,
  `DDraw off`) как «сервер симуляции»; единственное видимое окно — GMod.
- **Плюсы:** честное «играем в 3D», один экран.
- **Минусы:** больше правок в TH4 (нужен настоящий headless-режим).

### Форма 3. Полный порт логики в GMod
- **Не рекомендуется.** TH4 — это десятки тысяч строк деобфусцированного кода.

**Рекомендация:** начать с **Формы 1 + Варианта C**, спроектировать протокол так, чтобы
безболезненно перейти к **Форме 2 + Варианту A**.

## Развилка №3: потребитель

- **Клиентский аддон GMod** (одиночная игра, один игрок, TH4 на той же машине).
  → Рекомендуется для MVP.
- **GMod-сервер** (дедик, много игроков, каждый со своим TH4) — на порядок сложнее,
  отложить. См. `08-otkrytye-voprosy.md`.

## Слои системы (предлагаемая модульность)

1. **Источник (`th4-export`)** — внутри/рядом с TH4. Умеет: снимок мира, поток дельт,
   приём команд. Транспорт-агностичен.
2. **Протокол (`d1api`)** — схема данных + версия. Не зависит от движка.
3. **Транспорт** — named pipe / TCP / shared memory / HTTP/WebSocket (выбирается).
4. **SDK** — обёртки для потребителей (Lua-модуль для GMod, библиотека для C#/C++ и т.д.).
5. **Представление (`gmod-d1th4`)** — GMod-аддон: рендер мира, камера, ввод, UI.

Такая нарезка делает API универсальным: «любая игра берёт данные из Diablo 1».

## Что даёт существующий код TH4 (зацепки)

- **`DungeonInfo`** (в `src/game.h`) — уже готовая агрегация ВСЕГО мира в один сериализуемый
  блок (игрок, карты, предметы, снаряды, монстры, объекты, свет, авто-карта). Это, по сути,
  готовый «снимок мира» для сохранения → идеальная основа для экспорта состояния.
- **`Sync`/`multi`/`Net`/`tmsg`** — существующий сетевой слой (turn-based модель Diablo).
- **`Server`/`Server.vNext.vcxproj`** — отдельный таргет «сервер» (см. `03`).
- **`lib/txt/*`** — база реверса с адресами/указателями (для варианта B).
