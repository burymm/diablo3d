# 00. Журнал решений

Короткие зафиксированные договорённости. Обновлять по мере уточнения.

## Р-1. Вид камеры (3D)
**Решение (предварительно):** цель — **от первого лица** (максимально атмосферно).
Как запасные варианты — от третьего лица или вращаемая камера. Понимаем, что FP сложнее
(нужно свободно передвигаться, камера не должна проваливаться в стены, свои спрайты вблизи
выглядят плоскими). Поэтому делаем **FP как цель**, но архитектуру камеры — переключаемой.

**Следствия:**
- на первых вехах камера может быть от третьего лица/вращаемой — это дешевле для отладки;
- для FP позже понадобится: коллизия камеры, «тело» или его отсутствие, отдельная модель
  рук/оружия, `viewmodel`.

## Р-2. Источник данных (гибрид)
**Решение:** MVP — **внешнее чтение памяти** процесса `TH4.exe` (игру не трогаем).
Перспективная цель — **инструментировать исходники TH4** (стабильные смещения, события,
инъекция команд), когда мы убедимся, что форк собирается.

**Модель, как её понимает заказчик:** «TH4 считает игру → мы копируем его данные из памяти
→ показываем/играем в GMod». Это и есть Вариант B на старте.

## Р-3. Управление
**Решение:** **WASD + мышь.**

**Следствия и риск:**
- TH4 — авторитет и его движение «клик-в-точку» (pathfinding). Мы будем переводить
  WASD-намерение в команды движения TH4, а результат читать обратно.
- Из-за цикла «команда → TH4 → чтение обратно» возможна **задержка** управления. Это
  главный риск для FP-ощущений. Варианты смягчения — в `11-upravlenie-i-kamera.md`.

## Р-4. Первый практический шаг
**Решение:** собрать **самый простой сквозной прототип**: убедиться, что мы вообще можем
прочитать из памяти TH4 реальные данные и передать их в GMod. Детали — `10-mvp-spike.md`.

## Р-5. Универсальность API
**Решение (без изменений):** проектируем транспорт/протокол так, чтобы им мог
воспользоваться любой движок, а не только GMod (`05-most-i-api.md`).

## Р-6. Название проекта
**Решение:** проект называется **`diablo-1-source`**. Папка проекта приведена к этому имени:
`e:\games\diablo-1-source\`. Имя «The Hell…» не используем (требование лицензии TH4).

## Р-7. Целевая версия игры
**Решение:** тестируем на **TH4 alpha 0.772** (ваша установленная сборка). Все смещения/адреса
памяти привязываем к этой версии; при обновлении игры — снимаем заново (см. Р-9).

## Р-8. Управление — допустим «клик-фолбэк»
**Решение:** хотим FPS, но допускаем эмуляцию кликов (движение = «клик в точку перед собой»,
атака = «клик по цели»), если так проще и надёжнее. Официально допустимый путь для MVP/FP.

## Р-9. Идея «инициализации» адресов (подтверждена)
Согласовано: сначала **один раз** проводим инициализацию — находим адреса (offset-карта для
0.772), затем читаем/пишем по ним. Поиск — вручную (Cheat Engine) и/или сигнатурами по коду.
Offset-карту храним с привязкой к версии exe.

## Р-10. Главная цель этапа — проверить играбельность
**Решение:** задача сейчас — проверить **гипотезу**, а не построить всё. Суть:
- читаем координаты/состояние из Diablo,
- отправляем обратно команды (движение = клик перед собой и т.п.),
- смотрим, ощущается ли это **играбельно**.
Свою сборку `TH4.exe` из исходников делаем позже, если будет интересно/нужно.

## Р-11. Живой `Player` найден в куче (13.10.2026)
**Решение:** читать состояние из запущенного процесса по **эмпирической карте смещений**
(см. `13-karta-pamyati-th4.md`), а не по смещениям из клона исходников — они не совпадают.

**Факты:** живой `Player` (`0xDE7988` в сессии) лежит в куче без статического указателя в
модуле; есть **две синхронные копии** (античит-дублирование). Раскладка запущенной сборки
отличается от `structs.h`: префикс = клон **+4**, хвост = клон **−1**. Привязка — по строке
имени героя.

## Р-12. Offset-карта хранится в `bridge/reader/offsets.json`
**Решение:** рабочая карта полей (снятая с 0.772) — в `offsets.json`. При обновлении игры
адрес базы меняется после перезапуска → перезапускать `bootstrap`/`autofind` по имени героя.

## Р-13. Критерий спайка №1–3 выполнен
**Решение/факт:** reader читает живые HP/ману/золото/опыт/координаты и пишет **меняющийся**
`snapshot.json` в `garrysmod/data/d1bridge/`. Осталось: GMod-аддон (пункт №4) и обратный
канал. Детали реверса — `13-karta-pamyati-th4.md`.

## Р-14. Сквозной поток работает end-to-end (16.10.2026)
**Факт:** TH4 (0.772) → `d1reader.py watch` → `snapshot.json` → GMod-аддон `d1bridge.lua`.
Проверено в игре: герой `Iosia`, ур. 18, HP 45/45, мана, золото 9697, XP 722189,
Row/Col 50/83, dungeon 1. Критерий MVP-спайка №4 закрыт.

## Р-15. В структуре имя героя лежит ДВАЖДЫ
**Факт/правило:** в `Player` строка имени встречается по смещению `+0xA8` **и** ещё раз
по `+0xA8 + 0x174`. Поиск по имени цепляется за любое из них, поэтому `bootstrap`
подставлял базу со сдвигом `0x174` и все поля читались со смещением (нули/мусор).

**Правило на будущее:** после нахождения кандидата по имени обязательно проверять поля
(уровень, HP, координаты) по рабочей раскладке и брать тот base, где они осмысленные —
а не первый попавшийся. Для этого есть `findhero.py --apply`.

**Следствие:** античит держит **две синхронные копии** структуры; «живая» определяется по
`CurLife` — у дубликата она 0 или 1 HP. См. Р-11 и `13-karta-pamyati-th4.md`, раздел 6.1.

## Р-16. Обратный канал: клик в окно, а не запись в память (16.10.2026)
**Решение (этап 1):** команда из GMod доставляется в TH4 **синтетическим кликом
мыши в окно игры** (Р-8), а не записью в память героя. Файл-очередь:
`bridge_cmd.json` (пишет GMod) → reader опрашивает его каждые 20 мс →
клик; ответ (`ack`) липнет в `snapshot.json`.

**Следствия:**
- Смещения в памяти TH4 для управления не нужны — работает на любой сборке.
- Каждая команда поднимает окно TH4 и забирает фокус. Это главное ограничение
  для режима «играть в GMod».
- Альтернативы (без фокуса): `PostMessage`, `SendInput`, запись в
  `destAction`, инъекция в TH4 — см. `15-obratnyy-kanal.md`.

## Р-17. Перед кликом обязательно проверять foreground
**Факт/правило:** синтетический клик идёт по **абсолютным экранным координатам**.
Если окно TH4 не на переднем плане, клик уходит в чужое приложение, а reader
всё равно отвечает `OK`. Поэтому `thclick.py` поднимает окно
(`SetForegroundWindow` + `AttachThreadInput`) и **проверяет** `GetForegroundWindow`;
при неудаче клик не выполняется, причина попадает в `ack`.

## Р-18. Дедупликация команд по `SysTime()` + `sid`
**Правило:** `seq` в GMod сбрасывается при рестарте, `os.time()` имеет
секундную точность (две команды в одну секунду схлопывались бы в одну).
Поэтому дедуп идёт по `ts = SysTime()`, а `sid` (id сессии GMod) сбрасывает
состояние дедупа при перезапуске GMod.

## Р-19. Частоты разделены: команды vs снимок
**Решение:** `watch` опрашивает команды каждые `--tick` (20 мс), а снимок
пишет каждые `--interval` (0.1 с = 10 Гц). Задержка ввода не должна зависеть
от частоты снимка. Плюс `read_player` читает весь префикс структуры **одним**
`ReadProcessMemory` вместо ~30 вызовов.

## Р-20. Ввод в TH4: курсор + серия WM_MOUSEMOVE, окно развёрнутое (16.10.2026)
**Факты, найденные экспериментом:**
1. TH4 **игнорирует координаты в `WM_LBUTTONDOWN`** и берёт позицию из
   **настоящего системного курсора**. Без `SetCursorPos` ввод не работает.
2. Перед кликом нужна **серия `WM_MOUSEMOVE`, разнесённая по кадрам**
   (3 × 30 мс). Одного сообщения мало: клик обрабатывался по **предыдущей**
   позиции — наблюдался сдвиг ровно на одну команду назад.
3. **Окно TH4 должно быть развёрнутым.** Свёрнутое — игра ввод не
   обрабатывает вообще. При этом окно может быть **не в фокусе** (перекрыто
   GMod или на втором мониторе) — проверено 8 из 8.

**Решение:** режим ввода по умолчанию — «курсор + PostMessage»: окно не
поднимаем, фокус не забираем, курсор пользователю возвращаем через ~0.3 с.
Настоящая кнопка (`SetForegroundWindow` + `mouse_event`) — запасной режим
`d1_mode cursor`.

> ⚠️ **Поправка к более ранней записи в этих же доках:** «свёрнутое окно
> работает» было ошибкой эксперимента (курсор случайно лежал на проходимой
> клетке). Проверка с намеренно уведённым в сторону курсором опровергла это.

## Р-21. Геометрия экрана измерена, а не взята из исходников
**Факт:** тайл на экране TH4 — **128×64 px**, герой нарисован **на 64 px выше
центра окна**, формула `px = cx + (dRow−dCol)·64`, `py = cy − 64 + (dRow+dCol)·32`.
Таблица направлений отличается от «школьной» изометрии (`right` = `+1,−1`).
Клик нужно делать **точно в центр клетки**: на границе игра выбирает соседа
непредсказуемо. Константы — `SCREEN_GEOM`/`STEP_DIRS` в `d1reader.py`.

## Р-22. Задержка обратного канала: 0.2–0.45 с, мост тут не виноват
**Факт:** команда → подхват reader'ом 15 мс → служебные паузы ввода ~190 мс →
герой сдвигается через **209–454 мс (медиана 428)**. Оставшаяся задержка — внутри
TH4 (обработка клика, разворот, анимация шага).

**Следствие:** клик-фолбэк годится для «классического» управления, но не для
FPS. Для от первого лица нужны предсказание в GMod или команды внутри TH4
(`destAction`).

## Р-23. Удержание клавиши = СОСТОЯНИЕ в reader, а не поток команд
**Проблема, из-за которой переделали:** каждая команда дёргает системный курсор
(TH4 читает позицию именно с него), а клики во время ходьбы игра всё равно
игнорирует. Поток команд бил 2.2 раза в секунду — курсор в GMod прыгал
постоянно, а толку было мало.

**Решение:** GMod шлёт `{"action":"hold","dir":...}` один раз при нажатии и
`{"action":"hold","dir":null}` при отпускании. Reader сам кликает, когда герой
**стоит** (клетка не менялась >= 0.25 с), не чаще 0.9 с. Если герой не
двигается дольше 1.6 с — путь перекрыт: клики прекращаются до отпускания
клавиши, иначе курсор дёргался бы вхолостую.

**Измерено:** 0.9 клика/с и 1.8 скачка курсора/с против 2.2 и 4.4 у потока
команд — **в 2.4 раза реже**, при этом скорость выше: 2.7 кл/с в подземелье
(против 1.87 раньше). Побочный плюс: длинный шаг перестал быть проблемой —
при перекрытии мы не долбим по стене, а честно говорим об этом в `ack`.

## Р-25 (план). Самодостаточная сборка: exe сам публикует состояние в разделяемую память

**Цель:** убрать внешние скрипты поиска (`findhero.py`, сканирование памяти).
Сборка `th43d.exe` сама публикует всё нужное в **именованную разделяемую
память** (shared memory), а мост — только читает её.

**Почему shared memory, а не файл:**
- нет файлового I/O на каждом кадре (файл — только для отладки/логов);
- нет гонки «прочитал полузаписанный файл» — решается seq-счётчиком;
- имя фиксировано (`D1BridgeState`) — адреса в памяти больше не нужны;
- не требует драйвера/прав администратора (`Local\` в пределах сессии, `Global\` — если нужно);
- читать может любой процесс (Python reader, будущий GMod-модуль).

**Механизм (Win32):**
- в exe: `CreateFileMapping(INVALID_HANDLE_VALUE, NULL, PAGE_READWRITE, 0, SIZE, "D1BridgeState")`
  + `MapViewOfFile`; писать каждый кадр/по таймеру ~20–50 мс;
- в reader: `OpenFileMapping(FILE_MAP_READ, FALSE, "D1BridgeState")` + `MapViewOfFile`,
  читать через `ctypes` (функции уже есть в `d1reader.py`-стиле).

**Раскладка (предложение):**
```
Header (fixed):
  u32 magic   = 'D1B1'
  u32 version
  u32 seq       // seqlock: нечётный = идёт запись, чётный = стабильно
  u64 timestamp_ms
  Player: base, Row, Col, dir, HP, MaxHP, Mana, MaxMana, Level, XP, Gold, ClassID, name[32]
  counts: monsters, items
Body:
  i32 FineMap[112*112]
  u8  TileBlockWalking[2049]
  u8  PlayerMap[112*112]
  Monster monsters[N] {x, y, type, hp, flags}
  Item    items[N]    {x, y, type, flags}
```

**Консистентность (seqlock):** перед записью `seq++` (станет нечётным), после —
`seq++` (чётный). Reader: прочитал `seq`, данные, снова `seq`; если изменился
или нечётный — повторить. Никаких мьютексов в горячем пути.

**Итог:** `d1reader` (и GMod через `snapshot.json`) читают готовое состояние;
`findhero`/`scanmap`/`d1map_export` остаются только для отладки.
Файлы `d1map_export.txt`/`map.json` — опционально, для логов.

## Р-26. Shared memory реализована (20.10.2026)
**Решение:** Р-25 реализована. `th43d.exe` публикует состояние в именованную разделяемую память `D1BridgeState`.

**Что сделано:**
1. `src/d1bridge.cpp` — создание shared memory, публикация состояния через seqlock
2. `Main.cpp` — вызовы `D1BridgeInit()` в `WinMain`, `D1BridgePublish()` в `GameLogic`, `D1BridgeShutdown()` при выходе
3. `funcs.h` — декларации функций
4. `thehell3.vcxproj` — добавлен `d1bridge.cpp`
5. `bridge/reader/d1shm_reader.py` — Python-reader для чтения из shared memory
6. `bridge/reader/d1shm_test.py` — тестовый скрипт

**Формат shared memory:**
- Header: magic 'D1B1', version, seq (seqlock), timestamp
- Player: Row, Col, dir, dungeon, HP, Mana, Level, XP, Gold, ClassID, name[32]
- FineMap[112*112] — int32
- TileBlockWalking[2049] — uint8
- PlayerMap[112*112] — uint8

**Размер:** ~63 КБ

**Сборка:** `bridge\reader\build_th43d.bat` → `th43d.exe` (29 МБ)

## Р-28. Бинарный Lua-модуль GMod: прямое чтение shared memory (20.10.2026)
**Решение:** GMod читает `D1BridgeState` напрямую через DLL — без файлов и без Python-моста.

**Что сделано:**
1. `bridge/gmod/d1bridge_dll.cpp` — Lua-модуль: `open`, `close`, `read`, `send_command`, `is_open`
2. `bridge/gmod/lua.hpp` — заголовки Lua 5.1 (непрозрачный `lua_State`)
3. `bridge/gmod/d1bridge_dll.vcxproj` — проект MSBuild (x86, toolset v145)
4. `bridge/gmod/lua_shared.def` + `lua_shared.lib` — import library из экспортов GMod
5. `bridge/gmod/d1bridge.dll` — собранный модуль (86 КБ)
6. Установка: `garrysmod/lua/modules/d1bridge.dll`
7. `bridge/gmod/d1bridge.lua` — аддон читает через модуль, откат на `snapshot.json`

**Важные детали (не повторять!):**
- **GMod-клиент — x64!** С 2019 года Steam запускает `gmod_win64.exe`.
  Линковать против `garrysmod/bin/win64/lua_shared.dll` (64-бит).
  `garrysmod/bin/lua_shared.dll` (x86) — только для 32-битного `gmod.exe`.
- **Бинарные модули GMod лежат в `garrysmod/lua/includes/modules/`** (НЕ `lua/modules/`).
  В `lua/modules/` — только обычные Lua-модули.
- Если архитектура DLL не совпадает с клиентом — GMod молча падает на поиск `.lua`
  и выдаёт: `Couldn't include file 'includes\modules\d1bridge.lua' - File not found`.
- Свои заглушки Lua API **не работают**: GMod вызывает `luaopen_d1bridge` со своим
  `lua_State`, и функции API должны резолвиться в его VM. Заглушки дали бы пустые данные.
- Import library собирается из экспортов: `dumpbin /exports` → `.def` → `lib /DEF:... /MACHINE:X64`.
  В `.def` обязательно `LIBRARY lua_shared.dll` — иначе импорт будет `lua64_shared.dll`.
  Фильтровать экспорты нужно по regex `^\s+\d+\s+[0-9A-F]+\s+[0-9A-F]+\s+\S+` —
  иначе в `.def` попадёт мусор от dumpbin и линковка упадёт.
- `lua_State` достаточно сделать непрозрачным (`typedef struct lua_State lua_State;`) —
  полное определение не нужно.
- В `lua.hpp` нужен `<stdint.h>` — иначе `int32_t`/`uint32_t` не определены и каскадом
  ломаются все структуры.
- В bat-скриптах нельзя писать `echo текст (скобки)` внутри `if`-блока —
  `)` закрывает блок досрочно. Использовать `goto`-метки.

**Сборка (автоматизирована):**
```bash
cd bridge\gmod
build_d1bridge_dll.bat    # генерирует .lib, собирает x86+x64, выбирает нужный
cd ..\reader
d1bridge_install.bat      # ставит аддон + DLL в GMod
```

**Итог:** задержка чтения — мгновенная (прямой доступ к памяти), файлы не нужны.
Команды идут через `send_command` → `Player.destAction` в TH4.

## Р-30. Механика бинарных модулей GMod — полностью разобрана (20.10.2026)
**Решение:** выяснено, как GMod загружает бинарные Lua-модули. Р-28/29 доведены до конца.

### Как GMod грузит модуль (подтверждено экспериментом)

1. **Путь:** `garrysmod/lua/bin/gm<cl|sv>_<имя>_<арх>.dll`
   - `cl` — клиент, `sv` — сервер
   - арх: `win64` / `win32` / `linux64` / `osx64`
   - Штатная проверка GMod: `util.IsBinaryModuleInstalled("d1bridge")` →
     `file.Exists("lua/bin/gmcl_d1bridge_win64.dll", "MOD")`
2. **Экспорт:** `gmod13_open(lua_State* L, const char* path)`
   - GMod передаёт **полный путь к DLL** единственным аргументом
3. **Регистрация:** модуль **сам** регистрирует себя в `package.loaded[<имя>]`
   - имя выводится из пути: `gmcl_d1bridge_win64.dll` → `d1bridge`
4. **`require()` возвращает `nil`!** GMod кэширует модуль в `package.loaded`
   **до** вызова `gmod13_open`. Поэтому после `require` надо брать
   `package.loaded["<имя>"]`, а не возвращаемое значение.

### Ловушки (не повторять!)

- **Стандартный Lua не работает в GMod:** `package.path` = nil,
  `package.cpath` = nil, `package.loadlib` **отсутствует**, `require` ищет
  только `.lua` в `includes/modules/`. Ошибка:
  `Couldn't include file 'includes\modules\d1bridge.lua' - File not found or is empty`
- `file.Exists` с типом `"LUA"` **не видит .dll** — только тип `"MOD"`.
- `lua/includes/modules/` — папка для **.lua** модулей GMod, не для DLL.
- `lua/modules/` — тоже не то (там .lua).
- Клиент GMod — **x64** (`gmod_win64.exe`), `jit.arch = "x64"`,
  LuaJIT 2.1.0-beta3.
- DLL загружается GMod'ом при первом `require` и **держится залоченной** —
  пересобрать/заменить можно только после закрытия GMod. Для экспериментов
  использовать новое имя файла (напр. `gmcl_d1bdiag2_win64.dll`).
- Экспорт `luaopen_<имя>` **не используется** GMod — нужен именно `gmod13_open`.

### Итог

```
th43d.exe → D1BridgeState (shared memory) → gmcl_d1bridge_win64.dll → Lua → HUD
```
Никаких файлов и никакого Python-моста. Команды: `send_command` →
`Player.destAction` в TH4.

## Р-31. Нативное движение: `walkPath`, а не `destAction` (20.10.2026)
**Факт/правило:** в TH4 движение обрабатывается **НЕ через `destAction`**, а через
очередь `player.walkPath[0]`.

**Разбор исходников** (`vendor/the-hell-4-src/src/Player.cpp`):
- строки 6020–6058: игра читает `player.walkPath[0]` и по нему вызывает
  `StartWalkUp` / `StartWalkDown` / `StartWalkHorizontal`
- `destAction` в этой ветке обслуживает **только атаки и касты**
  (`PCMD_9/20/21/22/23/24/25/26`)
- `walkPath` заполняется функцией `MakePlayerPath()` → `FindPath()` с
  предикатом `CellFreeForPlayer` (проверка стен/мобов/объектов)

**Решение:** команда движения применяется так же, как TH4 делает это при клике
по клетке (`msg.cpp:1530-1531`):
```cpp
ClearPlayerPath(CurrentPlayerIndex);
MakePlayerPath(CurrentPlayerIndex, targetRow, targetCol, 1);
```
`MakePlayerPath` сама вызывает `FindPath` с `CellFreeForPlayer` — проверка
проходимости делается штатно, по правилам игры (стены, монстры, объекты).

**Смещения направлений** — источник истины: параметры `changeRow`/`changeCol`
в вызовах `StartWalk*` (`Player.cpp:6051-6058`):
```
1=UR( 0,-1) 2=UL(-1, 0) 3=DR(+1, 0) 4=DL( 0,+1)
5=U (-1,-1) 6=R (+1,-1) 7=D (+1,+1) 8=L (-1,+1)
```
Экранная изометрия TH4 (Р-21): `px = cx + (dRow-dCol)*64`, `py = cy + (dRow+dCol)*32`.

**Ловушка (исправлено):** сначала была написана таблица от руки
(`1=UR(+1,+1) 7=D(0,+1)`) — **2 из 8 направлений были неверны**:
`up-right` вёл вниз, `down` — вниз-влево. Проверяется только сверкой с
`StartWalk*` или эмпирическим тестом с логом `walkPath[0]`.

**Ловушка замера:** если команды отправлять подряд, не дожидаясь конца шага,
измеряется не задержка команды, а остаток текущего шага (в TH4 шаг ~300–500 мс).
Перед замером надо ждать, пока герой остановится (`d1shm_latency.py` это делает).

## Р-32. Версионирование раскладки shared memory (20.10.2026)
**Проблема:** DLL и TH4 собираются отдельно. После добавления поля в структуру
игрока (например `CurAction`) старая DLL читала данные со сдвигом 4 байта —
и данные героя, и **смещение команды** (96 vs 100) оказывались неверными.
Симптомы: «герой виден частично», «команды не срабатывают».

**Решение:** TH4 публикует **размер структуры игрока** в заголовке
(`header.player_size`, ранее неиспользуемое поле `padding`).
Читатели (DLL, Python) вычисляют смещения динамически:

```python
if player_size == 76: fields = PLAYER_FIELDS_V2   # с CurAction
else:                  fields = PLAYER_FIELDS_V1   # 72 байта, без CurAction
```

Дополнительно DLL экспортирует `abi_version()` — аддон проверяет его и
отбрасывает устаревшую сборку модуля, не падая.

**Поддерживаемые раскладки игрока:**
| Размер | Состав |
|--------|--------|
| 72 (v1) | Row, Col, dir, dungeon, CurLife, MaxCurLife, CurMana, MaxCurMana, CharLevel, ClassID, Xp, TotalGold, name |
| 76 (v2) | + CurAction, padding (после dungeon) |

**Правило на будущее:** при изменении структуры игрока в `d1bridge.cpp`
**обязательно** править `PLAYER_FIELDS_V1/V2` в `d1shm_reader.py` и
`D1PlayerField()` в `d1bridge_dll.cpp`.

## Р-31. GMod — мир Z-up! (20.10.2026)
**Ошибка:** движение работало только по одной оси (`move` всегда был `(±1, 0)`),
хотя камера вращалась (yaw менялся 52…307).

**Причина:** в GMod мир **Z-up**: X=восток, Y=север, Z=вверх.
Горизонтальная плоскость — **XY**. Компонента `.z` у вектора направления
(`Angle:Forward()`, `Angle:Right()`) — **вертикальная**, и при pitch=0 она всегда 0.

Код читал `f.z`/`r.z` — из-за этого вторая координата движения всегда была 0.
Аналогично, сцена строилась в плоскости XZ вместо XY.

**Правильно:**
```lua
local ang = Angle( 0, camYaw, 0 )
local f = ang:Forward()
local r = ang:Right()
-- горизонтальная плоскость — XY:
local fx, fy, rx, ry = f.x, f.y, r.x, r.y
```

И для сцены: `X = Col*CELL`, `Y = Row*CELL`, `Z = 0` (высота).

**Проверено:** задержка ввода **64–110 мс** (медиана 91) против 209–454 мс
у клик-фолбэка. Управление работает и в городе, и в подземельях.

## Р-34. bat-файлы после правки теряют CRLF (20.10.2026)
**Симптом:** скрипт падает с `The system cannot find the path specified` и
`'2' is not recognized as an internal or external command` — при этом
`cd /d "%~dp0..\gmod"` выглядит правильно.

**Причина:** bat-файл должен быть в кодировке **CRLF**. Инструмент правки
записывал его с **LF-only**, и `goto`/`if` в bat-скрипте ломают разбор
(строка склеивается со следующей).

**Правило:** после любой правки .bat проверять переводы строк:
```powershell
$b = [System.IO.File]::ReadAllBytes($f)
$t = [System.Text.Encoding]::UTF8.GetString($b)
([regex]::Matches($t, "`r`n")).Count   # должно быть > 0
```
Или конвертировать:
```powershell
$t = [System.IO.File]::ReadAllText($f) -replace "`r`n","`n" -replace "`n","`r`n"
[System.IO.File]::WriteAllText($f, $t, (New-Object System.Text.UTF8Encoding $false))
```

**Также исправлено:** в `build_d1bridge_dll.bat` был `cd /d "%~dp0..\gmod"`
хотя скрипт сам лежит в `bridge/gmod` — правильно `cd /d "%~dp0"`.
И добавлена автоустановка DLL в GMod в конце скрипта (чтобы версии не расходились).

## Р-35. Изометрия TH4 воспроизводится камерой GMod — точный ракурс (20.10.2026)
**Симптом:** пользователь смотрит на 3D-сцену и говорит «вижу старые 3д-картинки,
уровень остался как был». Данные были верные (`d1scene_info` показывал
область 57×57, стены 900, герой R62 C72), но картинка не менялась.

**Причина (две, обе реальные):**
1. `d1scene.lua` брал углы камеры из `D1Control.GetYaw()/GetPitch()`, а те, в
   свою очередь, брались из угла взгляда игрока GMod (`EyeAngles()`) — то есть
   yaw был произвольным, а pitch ≈ 0. Камера смотрела почти горизонтально на
   пол, и изометрии TH4 не было видно. «Старые картинки» — это была та же
   геометрия, просто под чужим ракурсом.
2. Меши пола создавались заново **каждый кадр** в `drawScene()` — тяжело и
   без кэша.

**Решение — точная геометрия изометрии TH4.**
TH4 рисует карту так:
```
px = (dRow - dCol) * 64        (вправо)
py = (dRow + dCol) * 32        (вниз)
```
Этот 2D-вид **точно** воспроизводится в 3D-мире GMod при:
| Что | Значение |
|-----|----------|
| Мир (Z-up) | `X = Col * k`, `Y = Row * k` |
| Камера | `yaw = 225°`, `pitch = +30°` (вниз) |
| «Вперёд» (W) | → `PCMD_5` (вверх по экрану TH4) |
| «Вправо» (D) | → `PCMD_6` (вправо по экрану TH4) |

Проверено расчётом (не на глаз): при `yaw=225°, pitch=+30°` проекция всех
8 направлений TH4 даёт ровно TH4-координаты — расхождение 0 px:
```
PCMD_5 up        3D->(   0, -64)  TH4->(   0, -64)  OK
PCMD_1 up-right  3D->(  64, -32)  TH4->(  64, -32)  OK
PCMD_2 up-left   3D->( -64, -32)  TH4->( -64, -32)  OK
PCMD_6 right     3D->( 128,   0)  TH4->( 128,   0)  OK
PCMD_7 down      3D->(   0,  64)  TH4->(   0,  64)  OK
PCMD_3 down-right3D->(  64,  32)  TH4->(  64,  32)  OK
PCMD_4 down-left 3D->( -64,  32)  TH4->( -64,  32)  OK
PCMD_8 left      3D->(-128,   0)  TH4->(-128,   0)  OK
```
**Важно:** это работает в **правой** системе GMod (Z-up, X=восток, Y=север),
где `right = (sin yaw, -cos yaw, 0)`. Если бы мир был Y-up, знак «вправо»
перевернулся бы.

**Как это устроено в коде:**
* `d1control.lua`: константы `TH4_BASE_YAW = 225`, `TH4_BASE_PITCH = 30`.
  Камера = базовый ракурс **+ поворот мышью от него** (разница между текущим
  `EyeAngles()` и углом взгляда в момент загрузки). То есть по умолчанию вид
  — ровно изометрия TH4, а мышь её вращает (FPS-режим, как просил пользователь).
* `d1control.lua`: `DIR_VECTORS` в координатах `(X = dCol, Y = dRow)` — 8
  направлений ложатся ровно через 45°, поэтому «ближайшее направление»
  ищется сравнением yaw без приближений.
* `d1scene.lua`: `cellToWorld(row, col) = (col*CELL, row*CELL)` — тот же
  мир, что и в контроллере.
* `d1scene.lua`: FOV 40 + камера на 1900 юнитов (высота 1097 = `1900*tan(30°)`)
  — узкий угол обзора и большое расстояние дают вид, близкий к
  ортогональной изометрии TH4.

**Побочные правки сцены:**
* Меши кэшируются и пересобираются только при смене области карты.
* Набор мешей **фиксирован** (5 оттенков пола + стены + герой). Если бы имя
  меша зависело от ID тайла, старые меши остались бы в кэше движка и
  дорисовывались бы поверх новых.
* `d1scene_toggle` чистит меши (`mesh.Clear` + пустой меш), иначе выключенная
  сцена осталась бы на экране.
* Скрыт локальный игрок (`SetNoDraw`) — камера теперь в 1900 юнитах.
* Новая команда `d1scene_ascii` — ASCII-карта области (сверка с TH4).

**Результат:** 3D-сцена по умолчанию — это изометрия TH4 на настоящих данных
уровня (`FineMap`/`TileBlockWalking` из shared memory), а WASD работает
относительно камеры, как в FPS.

## Р-36. API GMod в этой сборке: IMesh, а не Start/End (20.10.2026)
**Симптом:** сцена не рисовалась вообще; ошибки вида
`attempt to call field 'Start' (a nil value)`, `called mesh.Begin with a bad
primitive type (20)`, `attempt to call field 'OverrideViewOrigin'`.

**Выяснено зондами** (методика и полные таблицы — `docs/17-gmod-api-ogranicheniya.md`):
* `mesh` — immediate-mode IMesh: `Begin(type 0..7, count, [material])`,
  `Quad(v1..v4)`, `End`. `mesh.Start`/`Clear`/`SetColor` **не существуют**.
* `render` полон (142 фн.), но `OverrideViewOrigin/Angles/FOV` **отсутствуют**.
* `surface.DrawPoly` **не рисует** (5 вариантов формата/обхода);
  `DrawRect`/`DrawTexturedRect*` работают.
* Хуки: работают `Think`, `Tick`, `PreRender`, `PostRender`, **`RenderScene`**,
  **`DrawOverlay`**, `HUDShouldDraw`; **не** работают `PreDraw`, `PostDraw`,
  **`HUDPaint`**, **`CalcView`** (вызывается, но значения возврата
  игнорируются), `ViewVectors`, `PlayerButtonPress`.
* **Работает `cam.Start3D(pos, ang, scale)`** — единственный способ задать
  свой ракурс (проверено визуально: куб «сверху» вместо «снизу»).

**Решения:**
* Отправка геометрии — только в `RenderScene` (не в `Think`: батч успевал
  уйти до рендер-фазы и пропадал).
* Своя камера — `cam.Start3D` + `render.ClearDepth()` перед блоком
  (иначе глубина песочницы перекрывает уровень; внутри блока глубина
  работает, и стены сортируются сами).
* Цвет — `render.SetColorMaterial` + `mesh.Begin(type, count)` (режим `A2`):
  не зависит от `$vertexcolor` у материала.
* 2D-интерфейс — `DrawOverlay` (обычный HUD недоступен).

## Р-37. Изометрия TH4 воспроизводится в 3D до пикселя (20.10.2026)
**Вывод (расчётом, проверено на всех 8 направлениях):**
мир `X = Col·k`, `Y = Row·k` (Z-up), камера `yaw = 225°`, `pitch = +30°`
даёт проекцию **ровно** TH4: `px = (dRow−dCol)·64`, `py = (dRow+dCol)·32`.
Расхождение 0 px; «вперёд» → `PCMD_5`, «вправо» → `PCMD_6`.

**Важно:** работает только в правой системе GMod (Z-up,
`right = (sin yaw, −cos yaw)`), иначе «вправо» переворачивается.

Полная математика + следствия — `docs/18-geometriya-izometrii-th4.md`.

## Р-38. Цель переформулирована: «поиграть в Diablo в 3D» (20.10.2026)
**Формулировка владельца:** играть в Diablo в 3D, причём «пострелять» как в
Heretic/Hexen, но на хардкоре и на рандомных уровнях Diablo.

**Следствие для архитектуры:** GMod-сервер **наш** → доступны серверные
скрипты и энтыти. Значит:
* TH4 остаётся источником правды (её ИИ, лут, магия, hardcore, рандомные
  уровни — бесплатно), а мы делаем 3D-представление + пульт;
* сервер читает SHM напрямую (`sv_d1bridge_win64.dll` — тот же бинарник,
  установлен ✓), двигает игрока в клетку героя и спавнит энтыти;
* клиент отправляет команды (ходьба уже работает; остаётся атака).

План по шагам — `docs/19-plan-3d-shooter.md`.

## Р-39. Портировать механику TH4 в GMod — отклонено (20.10.2026)
**Предложение владельца:** раз есть исходники TH4 — импортировать механику
и не ориентироваться на оригинал.

**Оценка:** это не «импорт», а новая реализация. TH4 — C++ под DirectX 9,
логика завязана на движок; объём (движение/коллизии, 8 классов монстров с ИИ,
предметы, лут, генерация уровней, ~100 эффектов магии, скриптовые события
`dungeon.txt`, анимации, звук, сеть) — десятки тысяч строк, т.е. отдельный
проект на месяцы.

**Решение:** не делать. Принцип проекта («логика живёт в TH4, GMod —
представление», `docs/01`, принцип 1) сохраняется; он же даёт 90% ценности
при 10% усилий. Частичный вариант («перенести только правила перемещения»,
~1–2 тыс. строк) оставить открытым как возможный поздний этап.
