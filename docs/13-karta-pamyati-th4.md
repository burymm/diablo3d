# 13. Карта памяти TH4 (запущенная сборка) — результаты реверса

Документ фиксирует **практические результаты** чтения памяти `TH4.exe` по состоянию на
13.10.2026 (сборка alpha 0.772). Это «offset-карта» для спайка. Адреса привязаны к сессии;
смещения (от базы `Player`) — к версии exe.

## 1. Процесс и модуль

- Имя процесса: **`TH4.exe`**, ровно один инстанс.
- Разрядность: **32-бит (WOW64)**. Из 64-битного Python чтение требует **прав администратора**.
- Модуль: base `0x01400000`, size `0x081AB000` (меняется от запуска к запуску — не хардкодить).
- Верхняя граница сканирования памяти: `0x7FFF0000`.

Команда проверки: `python d1reader.py info`.

## 2. Где живёт живое состояние (главный вывод)

Живой `Player` **не имеет статического указателя** в модуле. Он лежит в куче. Найдено
**две идентичные синхронные копии** структуры (античит-дублирование — заказчик был прав):

| Копия | Базовый адрес (эта сессия) | Комментарий |
|-------|----------------------------|-------------|
| copy1 | `0x00DE7988`                 | рабочая, обновляется при игре |
| copy2 | `0x00F692AC` (≈ `0xF692AB`)  | идентична copy1 |

Обе копии меняются синхронно (проверено: XP/HP/мана/золото совпадают). Для чтения
используем **copy1 = `0xDE7988`**. Адрес меняется после перезапуска игры → нужен рескан по
имени героя (`bootstrap`/`autofind`).

> Ранее по ошибке структура считалась «статическим снимком»: мониторинг `watch_multi.py`
> показал 0 изменений, потому что проверялись поля по «неправильным» смещениям и герой
> в тот момент просто не менял HP/опыт. При ходьбе/бое копии **обновляются**.

## 3. Раскладка структуры в запущенной сборке

**Клона исходников недостаточно:** запущенная сборка **отличается** от `structs.h` в клоне.
Различие **неоднородное**:

- **Префикс** (координаты/служебные поля) = смещение в клоне **+4 байта**.
- **Хвост** (флаги, имя, характеристики) = смещение в клоне **−1 байт**.
- Первый байт аргумента: база `Player` в памяти **выровнена по 8** (`0xDE7988 % 8 == 0`).

фиксированы. Значения-«якоря» для ручной проверки: имя, `CharLevel`, HP, мана, золото, `Xp`.

### Что ещё НЕ найдено / не подтверждено

- `xOfs/yOfs/xVel/yVel` и `Appearance` — смещения из гипотезы «префикс +4» дают мусор.
  Нужны для **плавной интерполяции** между клетками; пока обходимся дискретными `Row/Col`.
- `destAction`/`destParam1..4` (будущий обратный канал) — не проверены.
- Инвентарь (`Item`, `InvItemCount`), монстры, карты мира (`PlayerMap`/`TileMap`/`LightMap`)
  — не искались.
- `walkPath` в запущенной сборке выглядит иначе (наблюдался массив пар `(row,col)`), не как
  массив направлений в клоне.

## 4. Полезные факты

- **HP/мана — fixed-point (×64).** `CurLife=3200` при реальном значении 50.
- **Сейв зашифрован** (`CodeSave`: блочный XOR с SHA1-цепочкой) и меньше `sizeof(Player)` —
  читать состояние из сейва **нецелесообразно**.
- Из компилятора (проектный `stdafx.h`, v145): `sizeof(Player)=0x18448` (99400),
  `sizeof(Item)=0x204` (516), `sizeof(LastPlayerInfo)=0x3350`. Таблица версий даёт
  `StructSize<Player>(27)=0x18000` → `static_assert` не сходится (клон новее релиза).
- `CurSaveVersion = 27`, `CurItemGenVersion = 7`.

## 5. Метод, которым нашли (воспроизводимо)

1. `bootstrap --name "Iosia"` / `autofind` — скан по строке имени, кандидаты `Player`.
2. **Скан по значению** (`scan`/`narrow`, Cheat-Engine-стиль) по `Xp` (i64) и другим якорям.
3. **Дифф памяти при движении** (`diffheap.py`, `findpos.py`): два снимка региона с паузой →
   находим адреса, которые меняются (координаты, анимация, опыт).
4. Сверка с UI игры (золото, HP, уровень) — подтверждает, что читаем верное.

> **Важно при сканировании:** базы «игрока» не выровнены по 4/8 относительно нуля региона,
> поэтому в сканах использовать `--align 1`, иначе поля можно пропустить.

## 6.1. Что было исправлено 16.10.2026 (мост не показывал героя)

Симптом: после перезапуска игры `watch` писал `IsExists=0`, пустое имя, нули; затем
`autofind`/`bootstrap` находили кандидата по имени, но `watch` показывал нули и уровень 0.

Причина — **несогласованность раскладок**. Поиск и валидация кандидатов
(`find_player_candidates`, `validate_player`) использовали **смещения клона**
(`PLAYER_FIELDS`, `name_off=0xA9`), а чтение в `watch` — **эмпирические** из `offsets.json`
(`name_off=0xA8`). Клон на 1 байт больше в хвосте, поэтому валидатор пропускал/отбрасывал
не те структуры, а `autofind` вдобавок **перезаписывал** `offsets.json` клон-оверсетами,
ломая рабочую карту.

Исправлено:

1. Добавлена `load_empirical_layout()` — читает раскладку из `offsets.json`;
   `find_player_candidates` и `validate_player` работают по ней (клон — только фолбэк).
2. `bootstrap` и `autofind` больше **не затирают** смещения: сохраняются прежние `fields`,
   `name_off`, `flags_off`, обновляются только база/указатель/имя.
3. `atomic_write_json` — при `PermissionError` (GMod держит `snapshot.json`) делает
   несколько попыток и fallback на прямую запись; раньше reader падал с `WinError 5`.
4. `watch` — **авто-восстановление**: если структура по сохранённому адресу невалидна
   (`IsExists=0` / пустое имя / нулевой уровень) 25 кадров подряд, а известно имя героя,
   выполняется повторный поиск и `offsets.json` обновляется на лету.

**Правило на будущее:** раскладку запущенной сборки нельзя перезаписывать производными от
клона — она снимается один раз и хранится в `offsets.json`; `autofind`/`bootstrap` обязаны
её сохранять.

## 8. Обратный канал (16.10.2026) — что он дал для карты памяти

Этап 1 (клик в окно) не требует смещений в TH4, но при его отладке получено
две полезные поправки к таблице выше:

1. **`CursorRow` (`0x123`) и `CursorCol` (`0x125`) — НЕ позиция курсора.**
   При кликах в окно игры (и при движении мыши по экрану) в них наблюдались
   значения `0,0` и `0,-1`. Значит либо смещения неверны, либо это поля
   относительного смещения курсора, а не клетки. **Позиция курсора TH4 пока не
   читается** — для команд «клик по клетке» её надо либо найти, либо не читать
   вовсе (мы и так не читаем: клик задаётся в пикселях окна).
2. **Герой может умереть, и это видно по `CurLife` (`0xEB`).** Мёртвый герой
   не реагирует на клики — при тестах обратного канала это выглядело как
   «мост сломан». Проверка `CurLife > 0` обязательна перед тестом
   (`clicktest.py` это делает и предупреждает).
3. **`dir` (`0x58`) не меняется при ходьбе.** Во время тестов 8 из 8
   направлений поле оставалось `6`, хотя герой явно двигался в разные стороны.
   Значит смещение `0x58` — **не** «куда смотрит герой» (или читается не то
   поле). Для управления оно не нужно: направление задаётся нами.

Смещения `destAction`/`destParam1..4` (альтернатива клику — запись команды
в героя) по-прежнему **не подтверждены**. См. `15-obratnyy-kanal.md`.
