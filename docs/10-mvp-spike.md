# 10. MVP-спайк: «достать хоть какие-то данные из памяти TH4»

Цель спайка — **доказать сквозной поток данных** самым дешёвым способом:

```
TH4.exe (работает)  →  [reader.exe/py: чтение памяти]  →  snapshot.json
                                                            │
                                          GMod (Lua) читает файл и показывает данные
```

Не цель спайка: полная карта, 3D-геометрия, красивый рендер. Только «есть контакт» и
проверка играбельности.

## Целевая версия
**TH4 alpha 0.772** (установленная сборка). Все адреса/смещения привязываются к ней.
Порядок: **инициализация** (находим адреса) → **работа по адресам** (читаем/пишем).

## Гипотеза, которую проверяем (две стороны)

Гипотеза «будет ли играбельно» = два направления данных одновременно:

1. **Diablo → GMod:** читаем состояние (координаты героя, HP/мана, уровень, позже — монстры,
   карта).
2. **GMod → Diablo:** отправляем команды управления. Простейший вариант — **эмуляция кликов**
   (движение = клик в точку перед собой, атака = клик по цели). Более «правильный» вариант —
   внутренние команды TH4 (`destAction` и т.п., см. `05-most-i-api.md`).

Ощущение играбельности зависит в первую очередь от **задержки** цикла
«команда → TH4 → чтение обратно → показ» (см. `11-upravlenie-i-kamera.md`).

## Про «инициализацию»
Один раз находим адреса для версии 0.772 (руками в Cheat Engine и/или сигнатурами по коду),
сохраняем offset-карту и далее просто читаем/пишем по ней. Это быстрее, чем искать каждый раз.

## Критерий успеха (acceptance)

Минимально:
1. Reader находит в памяти `TH4.exe` **процесс** и читает оттуда хотя бы одно реальное
   игровое значение (например: имя персонажа, HP, ману, координаты, dlvl).
2. Значение **меняется во времени**, когда мы играем (урон → HP падает; ходьба → координаты
   меняются).
3. Reader пишет `snapshot.json` в папку, доступную GMod (`garrysmod/data/d1bridge/`).
4. GMod-аддон читает файл и выводит значения на экран (HUD/консоль).

## Шаги

### Шаг 1. Простейший reader (любой удобный язык)
- Python (через `ctypes` + `ReadProcessMemory`) или C#/C++ — на выбор. Python быстрее всего
  для прототипа.
- Уметь: найти процесс по имени (`TH4.exe`), открыть с правами на чтение памяти, читать
  байты по адресу, определять базовый адрес модуля (`EnumProcessModules`/Toolhelp32).

### Шаг 2. Найти «якорь» — одно игровое значение
Самый надёжный первый якорь — **имя персонажа** (строка, которую мы знаем):
- сканируем память процесса на строку имени героя;
- находим её адрес;
- зная из исходников, что `Player::playerName` (`CharName`) — поле внутри `struct Player`
  (см. `structs.h`), вычисляем адрес самого `Player` и смежных полей.

Дополнительные якоря, которые удобно подтверждать вручную:
- `CurLife`/`MaxCurLife`, `CurMana`, `TotalGold`, `CharLevel` (по значению из игры);
- `PlayerRowPos`/`PlayerColPos` (координаты героя — меняются при ходьбе).

> ⚠️ Главный риск спайка: **смещения зависят от конкретной сборки `TH4.exe`**. Адреса из
> `vendor/.../lib/txt/*` — от другой/старой сборки. Поэтому сначала ищем динамически
> (по значению/строке), а не хардкодим адреса.

### Шаг 3. Найти массивы мира (после якоря)
Когда базовый доступ подтверждён — ищем тяжёлые структуры:
- `PlayerMap[112][112]` (проходимость) — char-массив;
- `MonsterMap[112][112]`, `ObjectsMap`, `ItemMap`, `TileMap[112*112]`, `LightMap`.
- Стратегии поиска:
  a) **сканирование по структуре**: массив узнаётся по размеру и характеру значений;
  b) **через код**: найти в памяти функцию, которая обращается к массиву (сигнатура из
     исходников) и вычислить адрес из инструкции — самый устойчивый способ;
  c) **через `DungeonInfo`**: блок сейва содержит карты рядом — можно опираться на
     относительное расположение полей (см. `game.h`), найдя сначала одно поле.
- Хранить offset-карту **отдельно по версии exe** (например, по хешу/hash сборки).

### Шаг 4. Снимок и передача в GMod
- Формат: `snapshot.json` (для MVP), записывать атомарно (write temp → rename), чтобы GMod
  никогда не читал полуфайл.
- Папка: `d:\SteamLibrary\steamapps\common\GarrysMod\garrysmod\data\d1bridge\`.
- GMod-прототип: `lua/autorun/client/*.lua` → таймер `file.Read("d1bridge/snapshot.json","DATA")`
  → парсинг (JSON есть в GMod: `util.JSONToTable`) → вывод.
- Частота MVP: 5–10 Гц достаточно, чтобы «увидеть».

### Шаг 5. Проверить и зафиксировать
- Стресс-тест: сколько чтений в секунду держит без просадки.
- Проверить на **разных сборках** `TH4.exe` (устойчивость поиска якорей).

## Инструменты, которые пригодятся
- **Cheat Engine** — для ручного поиска значений/указателей и проверки гипотез (быстро).
- **x64dbg / IDA/Ghidra** — для поиска ссылок на глобалы по коду.
- Огромная база реверса в репо: `vendor/the-hell-4-src/lib/txt/*`
  (`__POINTERS.txt`, `__DATA ADDRESSES.txt`, `_FUNCTIONS.txt`, `_MONSTERLIST.txt`, …) и
  `doc/DevNotes.txt` — карта того, что искать.

## Что делаем СЛЕДУЮЩИМ после успеха
Переходим к `06-2d-v-3d.md`: из снимка строим в GMod 3D-сцену (пол/стены/сущности).

## Заметки по безопасности
- Чтение памяти — пассивное, игру не ломает и не должно задевать её защиту (anti-dupe и
  т.п. работают с сейвами/сетью, не с чтением).
- Позже, при **инъекции команд**, понадобится аккуратность (это уже активное вмешательство).

## Кандидат на первый конкретный таргет (порядок)
1. `TH4.exe` (v0.772) найден, память читается.
2. Найдено имя героя → адрес `Player`.
3. Читаются `CurLife`, `CurMana`, `CharLevel`, `Row/Col`.
4. `snapshot.json` пишется и читается в GMod.
5. **Обратный канал:** простейший «клик в точку перед героем» → герой идёт в TH4.
6. Оценка задержки/ощущений → вывод об играбельности.
7. Только после этого — карта, монстры, полноценный 3D-вид.
